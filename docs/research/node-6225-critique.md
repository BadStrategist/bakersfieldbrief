## 2. Errors and overclaims

1. **calls-node, Section 2 header**: "Bitrate ~82 kbps (format bit_rate 81742)" and "Duration 6.28 s" are presented as measured properties of Calls clips. My clip measured 85,169 bps and 6.01 s. AAC VBR varies per call; the doc states one sample as a general property. Overclaim, low impact.
2. **calls-node, Section 1**: "The `hash` rotates; a hash+filename pair from an earlier poll returned 403 minutes later." Contradicted by direct observation: the doc's own example URL (`ldsnpkwy/6225/1789944494-61061.m4a`) still returns HTTP 200 many hours after it was first published in the doc and in a scratch file. Hash lifetime is uncharacterized, not "minutes."
3. **calls-node, Section 1 URL table**: "`https://www.broadcastify.com/calls/node/6225` (frequencies list: .../calls/node/6225/fids)" — the fids URL 404s. Correct URL is `/calls/fids/6225`.
4. **calls-node, Section 4**: "the node live-calls poll returns only the most recent ~224 calls" — single observation; my poll returned 25. Presenting the window size as a property of the endpoint is overclaiming.
5. **feed-audit, Section 5**: "downloads with the existing `_audio_url()` + `_download_archive()` helpers … and saves as `<fid>-<startTs>.mp3`" — `_download_archive` cannot do that; it hardcodes `FEED_ID` (14029) into the destination filename. The code plan as written would mislabel backup blocks as 14029 blocks, silently corrupting source attribution.
6. **feed-audit, Section 5**: "Police coverage gap → 47440 (BPD + KCSO dispatch; exact same agencies…)" — agency identity confirmed only via feed titles, never via listening to the audio. The priority ranking 45474 > 40009 > 45166 has no measured basis at all.
7. **build-design, Section 5**: "Current: 16 blocks × ~3.65 MB ≈ 58 MB/night" — the window produces 18 blocks (~66 MB). Small but real arithmetic error that propagates into the wall-clock estimate.
8. **build-design, Section 4 data shapes**: claims the new row is a "superset of today's" and shows `"time_local": "05:42:17"` and `"epoch"`. Today's transcribe rows carry minute-level `%H:%M` time and no `epoch`. The doc asserts a property of existing code that is false.
9. **Both docs**: neither notices that `KO_MIN_CONF=0.45` is compared against negative `avg_logprob` values, so the low-confidence drop branch in `transcribe()` effectively never fires on the confidence half (the gate is `duration < 3.0` in practice), and that `digest.py`/`run.py` use a different constant (-0.45). Any design that says "reuse the same gate" inherits a broken gate.
10. **build-design, Section 5**: "Typical dispatch traffic … roughly 400–800 calls/night (UNVERIFIED)" — honestly flagged, but my one 25-call poll at ~09:40 PDT cannot support or refute it. Fine as written, remains open.
11. **feed-audit, Section 3**: "sample downloads 0.5–3.7 MB each" — my downloads were 3.24 KB (36357) to 3.73 MB; the 0.5 MB lower bound is plausible mid-day but not reproduced. Immaterial.

## 3. What survives (ranked by decision weight)

1. **The Calls list endpoint + sessionKey mechanism is real and reproduced exactly** (A1/A2): POST-only, sessionKey-required, JSON shape as documented. This is the foundation of the whole Calls build; it holds.
2. **Calls clip audio is real, downloadable with the premium cookie, and much better than the feed archives**: AAC, 96 kHz, mono, ~85 kbps in my sample vs 16 kbps / 22.05 kHz MP3 archives (A3/A4/B1).
3. **The feed bitrate table is correct** for all 6 feeds I re-probed (B1). The "no backup is better than 14029" conclusion is sound.
4. **The timing logic (C5/B7) is structurally sound**: the last blocks covering 05:00–06:00 close at 05:31–06:25 depending on feed, after the 05:20 job. The existing 06:45/07:00 jobs are the natural home for the tail; the docs' ~06:55 rule is conservative and correct.
5. **The compliance reading is confirmed against the live ToS**: Section 9 as quoted is real, verbatim, and covers the current pipeline exactly; Section 8 additionally bars non-personal use / republication without a license; Section 11 allows termination without notice (D1–D4).
6. **The repo description in the build-design is largely accurate** (function names, window, phases, preprocessing, cron lattice all check out, C1/C2/C6/C7), with three concrete defects: the block count (18 not 16), the assumed row shape (no epoch, minute-level time), and the feed-blind `_download_archive` naming.

**Compliance verdict.** The current pipeline (scheduled unattended archive downloads via `archives.php`/`play.php`, ffmpeg preprocessing, faster-whisper transcription, publication of derived news text to a public website plus social distribution) violates, on the face of the live text I fetched: Section 9(a) (scheduled automated downloading of archives and metadata), Section 9(b) (bulk downloading tooling), Section 9(c) (transcription and LLM processing of Broadcastify content), the Section 9 paragraphs stating a Premium subscription grants none of these rights and that non-commercial/purpose/scale do not matter, and Section 8 (use of site materials beyond "private, personal, non-commercial viewing purposes" and republication "on any other Web site" without a prior license). Section 11 lets Broadcastify terminate without notice. **What a bcfy.io Calls API license fixes**: programmatic access to Calls records and audio for the four node-6225 dispatch channels, and explicit coverage of transcription/AI pipelines. **What it does not fix**: (1) the Live Audio Feed Catalog is a *separate* product from the Calls Client API, so a Calls license does not by itself authorize the feed-14029 (or backup-feed) archive downloads the pipeline currently performs — that needs a Feed Catalog license; (2) Section 8 republication rights are a licensing question the Calls API terms do not obviously settle — publishing derived news text publicly still needs explicit permission or a clearance; (3) CHP/EMS/KCSO content can never come from Calls in this county. The compliance posture of the whole pipeline, not just the Calls experiment, must be settled before expanding any of it.

**Cheapest next action that most reduces the biggest remaining uncertainty**: one 20-minute run of the already-specced phase-0 spike S1 against the licensed path decision — request `https://bcfy.io/dev/apply/` terms and the Calls Client API pricing page (the only unclaimed artifact both docs said they did not fetch), because the build decision's GO branches all assume the license is obtainable, affordable, and actually covers transcription + county-scoped archives; if pricing is per-record-prohibitive, every downstream GO collapses to metadata-only or nothing.
